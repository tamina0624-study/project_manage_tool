01概要・対象範囲

本書は現行ソースから、構成、画面、機能、データ、APIと運用上の制約を整理した基本設計書である。関数単位の詳細設計と将来の機能案は対象外とする。

項目内容
利用目的案件と作業の可視化、対応漏れの防止、活動の振り返り。
主な利用者自身の案件・作業を管理する利用者。現行の保存方式は単一ユーザー・小規模データを前提とする。
対象プロジェクト管理、お気に入り、最近利用、チケット、ボード、スプリント日程、プロジェクトJSON入出力、テーマ切替。
未実装認証・権限、変更監査、同時更新の競合解決、Git情報の自動検出、PWA。
基準2026年10月19日時点の02.src/Web_baseとDBセットアップSQL。旧React/Vite時代の履歴は現行仕様の根拠にしない。

04機能・業務ルール

機能現行のルール
検索・並べ替え名前・パス・タグを大文字小文字を区別せず検索。タグ・お気に入りで絞り込み。保存順・名前・パス・最近利用順に対応。
プロジェクト名前・パス・タグ・ブランチ・リポジトリ状態を編集し、コメントを追加。Git情報は手動管理。ブラウザーから任意のローカルパスへ自由にアクセスする機能は持たない。
JSON入出力プロジェクト配列のみをprojects.jsonに出力。取込は配列またはdata配下の配列を受け付け、一覧全体を置換。チケット・スプリントのバックアップは含まない。
チケット入力プロジェクト・空白除去後のタイトルが必須。開始・終了日が両方ある場合は終了日が開始日より前なら保存しない。担当者、備考、親、スプリント等を設定。
採番内部IDはDate.now()を使用。表示IDは種別接頭辞＋既存最大番号の次番号（最低3桁、例：TASK-001）。編集可能でサーバー側の一意性保証はない。
種別・状態種別はBug / Feature / Task / Story / Epic。状態はtodo / doing / done。
状態変更時の日付共通日付更新処理では、todoで両日付を空にし、doingで未設定開始日を当日にして終了日を空にする。doneで未設定開始日と終了日を当日で補う。当日はブラウザーのローカル日付。
ボード表示Parent列は親IDなし・Epic以外。状態別3列は親IDありのチケット。Parentは保存する状態ではなく、Parent列へのドロップは変更しない。全チケットが必ずボードに表示されるわけではない。
チケット削除選択チケットと直接の子を削除。全子孫を再帰削除する実装ではない。
スプリントプロジェクト、名前、開始日、終了日を指定。終了日は開始日以降。関連はプロジェクトID＋スプリント名。スプリント編集・削除時に既存チケットを追随更新しない。
日程表示チケット日付が未設定の場合は表示用の仮日付を用いるため、棒の位置が確定予定を表すとは限らない。
テーマダーク・ライトの切替。初期状態はダーク。テーマの永続化は行わない。

入力チェックは主にブラウザー側。サーバー側に必須項目・参照整合性・重複ID・日付のスキーマ検証はない。

05データ設計

論理モデル

Project.id ← Ticket.projectId
Project.id ← Sprint.projectId
Ticket.id  ← Ticket.parentId（任意）
Project.id ← Recent[]
Sprintへの関連 = Ticket.projectId + Ticket.sprint（名前）

アプリケーション上の関連であり、DBの外部キー制約はない。

種別主要フィールド / 型
Projectid: number、name/path/gitBranch/repoStatus: string、favorite: boolean、tags: string[]、comments: array。
Ticketid/projectId/order: number、parentId: number|null、ticketId/title/sprint/ticketType/assignee/status/notes: string、startDate/endDate: string（日付または空。旧データでは未定義の場合あり）。
Sprintid/projectId: number、name: string、startDate/endDate: string（YYYY-MM-DD）。
RecentプロジェクトIDの数値配列。先頭ほど最近利用。

物理テーブル：project_manager_app_state

列SQLiteMySQL（API作成）制約・用途
idINTEGERINT主キー・自動採番。アプリ内IDとは別。
keyTEXTVARCHAR(64)NOT NULL / UNIQUE。projects、tickets、sprints、recent。
valueTEXTJSONNOT NULL。種別全体のJSON配列。
updated_atDATETIMETIMESTAMP初期値CURRENT_TIMESTAMP。MySQLは更新時も自動更新。SQLiteは挿入時のみ。

MySQLセットアップSQLではidがINT UNSIGNED、照合順序がutf8mb4_unicode_ci。APIの自動作成定義と細部に差がある。

保存単位

データ種別ごとの配列全体をUPSERTする。行単位のプロジェクト・チケットテーブルは持たない。複数端末の変更は後の保存で上書きされる。

localStorageのキーはprojectManagerProjects、projectManagerTickets、projectManagerSprints、projectManagerRecent。オリジン・ブラウザープロファイルごとに分離される。

06API設計

エンドポイントは同一公開ディレクトリのapi.php。actionをクエリに指定し、JSONを返す。

用途上のメソッドaction内容
GETprojects / tickets / sprints / recent種別全体を取得。
POSTsave-projects / save-tickets / save-sprints / save-recent本文のdataで種別全体を置換。
OPTIONS任意HTTP 204で終了。
GET api.php?action=tickets
応答: {"data": [...]}

POST api.php?action=save-tickets
Content-Type: application/json
本文: {"data": [...]}
応答: {"data": [...]}
状況現行の応答・処理
actionなし / 未知HTTP 400、missing_action / unsupported_action。
最終的なDB接続失敗HTTP 500、database_connection_failedと例外メッセージ。
不正JSON・data省略解析失敗の本文は空配列として扱う。dataが取れない場合は既存値を保存。HTTP 400で拒否する仕様ではない。
保存中の例外接続後の書込例外には共通のJSONエラーハンドラーがない。
GET・POSTはフロントエンドの利用規約。APIはOPTIONS以外をactionごとにメソッド制限していない。CORSはAccess-Control-Allow-Origin: *。認証・認可・CSRF対策は未実装。

07処理フロー

初期表示

  1. ハッシュから初期画面を選び、4種別のGET APIを並列に呼ぶ。
  2. APIは環境設定・DB接続を行い、必要ならテーブルを作成する。
  3. 既定サンプル状態にDB値を重ねて返す。DB読取失敗時は既定状態を返す。
  4. ブラウザーは取得結果を状態に取り込み、localStorageを更新して再描画する。
取得エラーは空配列に変換される。projectsが空ならlocalStorageまたはサンプルへ戻り、他種別も空なら既存状態・サンプルを維持する。正常な空状態と障害を区別せず、DBの空状態が画面へそのまま反映されるとは限らない。

保存

  1. 操作によりブラウザーの配列を更新。
  2. save-*へ種別全体を送信し、APIがUPSERT。
  3. localStorageを更新して再描画。

フロントエンドは保存APIのHTTPステータス・本文を検証しない。HTTP 500でも失敗を認識できない場合がある。通信例外はConsoleへ警告し、ローカル保存を継続。自動再送・競合解決はない。

DB切替

DB_DRIVER=sqlite → 指定SQLiteへ接続
それ以外        → MySQLへ接続
                   ├ 成功：MySQLを使用
                   └ 失敗：00.secret/project_manager.sqliteへ切替
                            └ SQLiteも失敗：HTTP 500

09非機能・制約

観点現状
規模・性能全体取得・全体保存、ブラウザー側検索・描画。ページング・負荷試験・応答時間保証はない。
同時更新排他、バージョン管理、マージ処理はない。後の保存で他端末の変更を失う可能性がある。
安全性HTMLエスケープ、PDOプレースホルダー、設定の公開範囲外配置を実施。ただし認証・権限・サーバー側スキーマ検証等は未実装。外部公開・共有運用には追加設計が必要。
整合性参照整合性・一意性はDBで保証しない。スプリント変更、親子削除、JSON取込で不整合が生じ得る。
障害・同期フォールバックはあるが、障害と空状態を区別しない。保存先・成功状態を画面で確実に識別する仕組みはない。
環境依存fetch、localStorage、FormData、ドラッグ等を使用。フォルダー選択・Clipboard APIはブラウザーと権限に依存。対応バージョンとモバイル操作は未確定。

認証、保存結果通知、入力検証、空状態処理、レコード単位更新、競合制御は今後の検討事項であり、実装済み機能に含めない。
